# Threat Model

> Draft section for the App Attest / DeviceCheck adoption-vs-enforcement paper.
> Audience: reviewers and co-authors. Two open decisions flagged at the end.

## System model

We consider the standard deployment of Apple's client-integrity primitives, App
Attest (`DCAppAttestService`) and DeviceCheck (`DCDevice`), introduced in iOS 11
(DeviceCheck) and iOS 14 (App Attest). A deployment comprises four parties:

1. **The client**, an iOS application distributed through the App Store, running on
   a consumer device. The app invokes the attestation APIs, which are backed by the
   device's **Secure Enclave**.
2. **Apple's attestation infrastructure**, which certifies, during enrollment, that
   an attestation key was generated by a genuine, unmodified instance of the app on
   a genuine Apple device, and which stores the two persistent bits of per-device
   state for DeviceCheck.
3. **The developer's backend**, which gates access to protected resources on the
   presence and validity of an attestation assertion or device token.
4. **The protected resource**, the asset the developer intends to make available
   only to legitimate app instances.

In the intended App Attest flow the client calls `generateKey`, then `attestKey`,
and sends the attestation object to the backend, which verifies it against Apple's
root and enrolls the public key bound to the relying-party identifier (Team ID
concatenated with bundle ID). For each subsequent sensitive request the client
calls `generateAssertion` over a hash of the request (the `clientDataHash`, ideally
incorporating a server-issued nonce), and the backend verifies the assertion
signature, the request binding, and a monotonically increasing counter before
serving the resource. In the intended DeviceCheck flow the client obtains a device
token via `generateToken`, and the backend queries Apple server-to-server to read
or update the device's two bits, for example to record that a per-device free trial
has been consumed.

## Assets

The assets a correct deployment protects are: (A1) revenue gated behind
authentication or entitlement, including subscriptions and free-trial eligibility;
(A2) per-device abuse state, chiefly the one-trial-per-device invariant; (A3) the
integrity of backend API requests, so that a request is honored only when it
originates from an unmodified app instance; and (A4) backend operating cost, where
an endpoint is computationally or financially expensive per call (for example an
endpoint fronting a paid third-party or AI service).

## Trust assumptions and trusted computing base

We treat the cryptographic primitives and Apple's infrastructure as sound. The
trusted computing base is the Secure Enclave, Apple's attestation certificate
chain, and Apple's server-side certification and DeviceCheck storage. We assume the
adversary cannot forge an Apple-signed attestation, extract a Secure Enclave
private key, or cause Apple to certify a modified binary. The security of a
deployment therefore rests on one assumption that is entirely the developer's
responsibility and is invisible from the client: **the backend correctly and
completely verifies the attestation evidence, and refuses the protected resource in
its absence.** Our threat model targets violations of this assumption.

## Adversary model

We define four adversary capabilities; a given attack composes one or more.

- **C1, Modified client.** The adversary re-signs the App Store binary with their
  own profile and injects code, or runs it on a jailbroken device, and can thus
  call, skip, or alter the attestation APIs and the surrounding business logic at
  will. The adversary runs on genuine Apple hardware.
- **C2, Network control.** The adversary observes and modifies traffic between the
  client and the backend (a man-in-the-middle position), and can strip, replay, or
  substitute attestation tokens and request bodies. This capability is amplified
  when the app does not pin, which our suite measures independently.
- **C3, Scale and automation.** The adversary operates many app instances or a
  device farm, or scripts the backend API directly, to convert a single bypass into
  mass abuse.
- **C4, Local state reset.** The adversary resets or circumvents any attestation
  state the client stores or trusts locally, including client-side records of trial
  consumption.

The adversary's goals correspond to the assets: obtain gated revenue without paying
(A1), defeat the one-trial-per-device invariant (A2), issue backend requests that
are honored despite originating from a modified or synthetic client (A3), and drive
backend cost through unauthorized use (A4). The adversary is economically rational:
they invest in a bypass only where the exposed value exceeds the effort, which we
reflect in the loss model.

Explicitly **out of scope**: breaking the Secure Enclave, Apple's certificate
chain, or TLS itself; compromising Apple's servers; physical device attacks; and
backend vulnerabilities unrelated to attestation (for example injection flaws). We
assume the primitives work as designed, and we study whether deployments use them
in a way that actually constrains C1 through C4.

## Enforcement failures

We say a deployment **enforces** attestation if and only if a request for a
protected resource that lacks a valid, fresh, request-bound assertion from an
enrolled genuine instance (for DeviceCheck: a server-validated token with correctly
interpreted bits) is rejected. A **misimplementation** is any deviation that admits
one of the adversary capabilities above. We organize the deviations into a failure
taxonomy, each class naming the capability that exploits it and the capability the
adversary thereby gains.

| Class | Enforcement failure | Exploited by | Adversary gains |
|---|---|---|---|
| F1 | Client adopts the API but the backend never verifies the evidence (adopt, not enforce) | C1 | Unrestricted access to A1 to A4 |
| F2 | Backend verifies one-time attestation (enrollment) but not per-request assertions | C1, C3 | Unattested API access after a single genuine enrollment |
| F3 | Assertion not bound to the request (`clientDataHash` unchecked) | C1, C2 | Request/parameter forgery with a valid assertion (A3) |
| F4 | No assertion counter or server nonce (replay protection absent) | C2, C3 | Replay of one assertion to scale actions |
| F5 | Incomplete validation of root CA, relying-party identifier, or environment (accepts development attestations) | C1 | Full bypass with a crafted or non-production client |
| F6 | DeviceCheck trial/abuse state gated client-side or on a client-asserted flag | C1, C4 | Unlimited trials, direct A1/A2 loss |
| F7 | DeviceCheck token minted or interpreted without server-to-Apple validation | C2, C4 | Token forgery or reset, trial farming |
| F8 | Device-keyed invariant assumed but gate keyed on account or other client-controlled identity | C3, C4 | New-identity trial and bonus farming |

Failures F1, F2, F5, F6, and F7 are total (the protection is absent); F3, F4, and
F8 are partial (the protection exists but is circumventable). A deployment may
exhibit several classes at once.

## Measurement-specific adversary note

A subtle confound, specific to iOS dynamic measurement, is that re-signing an App
Store binary strips Apple's restricted entitlements, which can make an unrelated
framework crash the app at launch. An uncorrected measurement would record this
crash as evidence of anti-tampering or attestation enforcement. Our threat model
distinguishes a deployment that **rejects the modified client at the server** (true
enforcement, the object of study) from one whose **modified client merely fails to
launch because of lost entitlements** (a measurement artifact). We neutralize the
latter so that C1 is realizable, and attribute a failure to enforcement only when a
bypassed request is served.

## Loss model and quantification methodology

The impact of a misimplementation is the value of the asset left exposed. For each
app in the corpus we determine, through static detection of adoption and the
differential enforcement battery, a tuple (adopts, enforces, asset class,
exposed-value estimate). We attach a conservative lower bound to the exposed value
per asset class using only public unit economics:

- **L1, Subscription and trial revenue (A1, A2).** For apps exhibiting F6 to F8, we
  take the App Store subscription or trial price as the per-instance value of a
  single bypass, and report the count of affected apps and the aggregate monthly
  price exposed per device. We do not multiply by a speculative device population;
  we report per-device and per-app exposure, which is a defensible floor.
- **L2, Backend cost amplification (A4).** For apps whose gated endpoint fronts a
  metered service, we estimate cost per unauthorized request from the provider's
  published pricing, combined with the observed absence of rate limiting, yielding a
  dollars-per-request-stream figure.
- **L3, API abuse and data exposure (A3).** For apps exhibiting F1 to F5 on content
  or data endpoints, we characterize what a single bypassed request returns (for
  example a page of otherwise gated records) as a qualitative severity, since dollar
  value is deployment-specific.
- **L4, Fraud and bonus abuse (A1, A2).** For signup, referral, and promotion
  endpoints reachable after bypass, we record the advertised bonus value as the
  per-instance exposure.

The aggregate result is reported as the fraction of adopting apps that do not
enforce, broken down by asset class, with a conservative lower-bound dollar
exposure for L1 and L2 where unit economics are public, and a severity
classification elsewhere. This yields a defensible headline of the form "of N apps
that adopt App Attest or DeviceCheck, M do not enforce it, exposing assets worth at
least X."

## Ethics and responsible disclosure

We demonstrate the absence of enforcement using the minimal evidence that a single
unattested or tampered request is served; we do not conduct mass abuse, farm trials
at scale, or exfiltrate user data, and all testing uses accounts and devices under
our control. Affected developers are notified before publication, and findings are
aggregated so that individual deployments are not operationally weaponized.

## Open decisions

1. **Formal definition of "enforcement."** The prose predicate above is usable, but
   we may want it stated as a security game or formal predicate to match the rest of
   the paper's formalism.
2. **L1 estimation granularity.** Keep L1 as a per-device lower-bound floor
   (defensible, conservative) or move to a modeled device-population estimate
   (riskier for reviewers, larger headline number).
